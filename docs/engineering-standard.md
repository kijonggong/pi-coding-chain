# 엔지니어링 정본

이 저장소에서 코드를 설계·변경·시험·검토·인계할 때 따르는 기준이다. 작업자 보고와 리뷰는
이 문서의 절 번호(예: 2.3, 3절)로 근거를 든다.

> 문맥 압축·복구·세션 교대 뒤에는 편집이나 코드 검토를 재개하기 전에 이 문서를 다시 읽는다(2.11).

## 2. 원칙

### 2.1 설계 우선과 책임 소재 (design first, responsibility assignment)

실행 흐름(예: Study의 protocol → 단계 함수 → 기록 → 수락·보고)에서 필요한 책임과 자료 흐름을 먼저 정한다.
기존 클래스·파일 배치는 유지의 전제가 아니다. 바뀐 뒤 누가 무엇을 소유하고 어느 소비자에게 전달하는지
한두 문장으로 적고, 기존 구현을 **유지·통합·교체·삭제**로 판정한다.

- 한 모듈은 한 책임을 갖는다(Single Responsibility Principle).
- 응집도는 높이고 결합도는 낮춘다.
- 파일 수나 줄 수를 맞추기 위해 책임을 기계적으로 나누거나 합치지 않는다.

### 2.2 근본 원인 수정과 불필요한 간접화 제거 (root-cause fix, unnecessary indirection)

- 결함은 원인이 있는 책임 자리에서 고친다. 그 옆이나 위에 같은 일을 하는 경로를 덧대거나 증상만 가리는
  workaround를 쓰지 않는다(3절).
- 명확한 역할 없이 값을 감쌌다가 즉시 풀거나, 같은 표현으로 왕복 변환하거나, 인자를 전달하기만 하는
  중간 계층을 만들지 않는다.
- 필요한 계산·형식 변환·시스템 경계가 없는 단계는 제거해 생산자와 소비자를 직접 연결한다.

### 2.3 대체하면 제거한다 (delete what you replace)

- 대체된 함수·분기·설정·시험·문서는 같은 변경에서 지운다(dead code elimination).
- 구현 전에 같은 책임의 모듈·저장소·유틸리티·실행 경로와 실제 호출자를 확인한다. 적합한 기존 기능을
  활용하고, 새 기능만을 위한 중복 구현(duplicated implementation)을 만들지 않는다.
- 기존 설계가 부적합하면 그 책임 위치를 개선하거나 교체한다. 같은 일을 하는 구현을 두 개 두지 않으며
  (no parallel implementation), 바꾼 공개 인터페이스의 호출 지점(call site)은 모두 찾아 함께 고친다.
- 남기는 임시 코드에는 제거 조건을 적는다.
- 지우기 전에는 그 코드가 왜 있는지 확인한다(Chesterton's fence). 안전 동작과 필요한 검증 범위는
  보존하되, 안전이라는 이름으로 구현·시험을 정리 대상에서 일괄 제외하지 않는다(2.9).

### 2.4 단일 출처와 구현 일관성 (Single Source of Truth, consistency)

- 상수·규칙·정의는 한 곳에 단위가 드러나는 이름으로 둔다. 파생값은 복사하지 않고 그 출처에서 계산한다.
- Magic Number와 근거 없는 하드코딩을 쓰지 않는다. 같은 지식을 두 곳에 적지 않는다(DRY).
- 같은 종류의 처리는 기존의 적합한 이름·인터페이스·처리 순서·오류 및 저장 방식을 따른다. 방식을 개선할
  때는 이유를 명시하고 관련 생산자·소비자·시험·문서를 함께 바꿔 같은 책임에 일관된 방식이 남게 한다.
- SHA 등 해시와 별도 영수증 파일은 기본 필수 항목이 아니다. 다음을 모두 설명할 수 있을 때만 쓴다.
  - 실제 소비자가 어떤 입력 변경·출처 오류를 구별해야 하는지
  - 그것을 Git·GitHub의 소스 이력, 기존 버전·입력 기록, 이미 읽은 자료로는 충족할 수 없는 이유
- 무결성·재현성이라는 이름만으로 단계마다 영수증을 추가하거나 같은 자료를 다시 해시하지 않는다.
  과거 자료를 읽기 위한 지원과, 새 실행에서 해당 기록을 생성·검사할 의무를 구분한다.

### 2.5 필요한 것만 만든다 (YAGNI)

현재 요구사항이나 도메인에 근거하지 않은 필드·파일·옵션·추상화·확장 지점을 만들지 않는다.
추가하는 정보는 의미와 실제 소비자, 그 소비자가 수행할 처리나 판단을 설명할 수 있어야 한다.
막연한 미래 사용이나 추적 가능성만으로 사용처 없는 정보(unused data)와 추측에 기반한 설계
(speculative generality)를 추가하지 않는다.

### 2.6 관심사 분리 (separation of concerns)

순수 계산(functional core)과 입출력·실행 같은 부작용(imperative shell)을 나눈다. 단계·실행 함수는 필요한
실행 순서와 부작용을 조율한다. 분리 자체를 목적으로 전달만 하는 함수·계층을 추가하지 않는다.

### 2.7 빠른 실패와 근거 있는 방어 (fail-fast, justified defensive programming)

- 실패는 원인별 이유 코드로 드러낸다. 조용한 대체(silent fallback), 오류 삼키기(error swallowing),
  기준 완화로 실패를 가리지 않는다.
- 방어 코드는 현재의 유효한 입력·상태 전이·외부 고장으로 발생 가능한 경로와 보호 대상을 근거로 둔다.
  같은 신뢰 경계에서 이미 보장돼 도달 불가능한 상태에 검사·정리·복구·재시도 분기를 추가하지 않는다
  (over-defensive programming).
- 발생 가능성이 낮은 고장과 구조상 발생할 수 없는 상태를 구분한다. 외부 입력, 동시 변경, 시간 경과,
  프로세스·장치 경계로 앞선 보장이 더는 성립하지 않으면 그 경계의 필요한 검사를 유지한다.

### 2.8 리팩토링과 의미 변경의 구분

- 동작 보존 리팩토링(behavior-preserving refactoring)과, 수치 방법·실험 의미가 바뀌는 의미 변경
  (semantic change)을 구분해 표시한다. 의미 변경은 원래 증거를 보존한다.
- 재사용은 선호이지 금지가 아니다. 유지·개선·교체를 실험 적합성, 정확성, 비용, 단순성, 검증 부담으로 비교한다.
- 수학 코드도 구조·중복·자료 변환·계산 비용의 검토 대상이다. 구현을 재작성하거나 최적화할 때는 수식,
  좌표계·단위, 수치 오차와 실패 동작을 대조한다. 동치인 구현 변경과 수학적 방법 변경을 구분하고,
  성능 개선은 같은 입력의 측정으로 확인한다. 구조의 복잡성과 실행 비용을 같은 문제로 단정하지 않는다.
- 최적화 후보는 실제 GPT Pro와 상의하고 로컬에서 확인한 뒤 채택한다.
- 변경 범위를 지킨다(scope discipline). 무관한 정리는 섞지 말고 기술 부채(technical debt) 후보로 기록한다.

### 2.9 계약 시험과 과검증 금지 (contract testing, no over-verification)

- 시험은 공개 계약의 의미를 독립 기대값(literal)으로 확인하는 최소한으로 둔다.
- 쓰지 않는 시험: 구현 세부에 묶인 시험(implementation-coupled test), 과잉 명세 시험(overspecified test),
  같은 사실의 반복 단정, 검증을 위한 검증 층(같은 파일 재해시, 중복 guard).
- 핵심 새 시험은 규칙을 일부러 틀리게 바꿨을 때 실패하는지 한 번 확인하고 원복한다(mutation check).
- 시험마다 다음을 확인한다.
  - 어떤 고장을 어느 실제 책임 경계에 주입하고, 어떤 관측으로 위반을 잡는지
  - 실제 생산자·소비자를 잇는지
  - 기대값이 구현에서 복사되지 않았는지
  - 대역이 결함을 대신 처리하거나 필요한 경로를 우회하지 않는지
  - 이미 다른 시험이 같은 경계를 충분히 확인하고 있지 않은지
- 같은 사실을 계층마다 재검사하는 guard·재해시, 코드 모양/호출 횟수만 고정하는 단정, 시험용 우회·wrapper와
  불필요한 중복 시험은 소유 책임 자리에서 삭제·통합한다. 필요한 고장 경계와 안전 동작 검출력은 남기며,
  기준 완화·skip·xfail·오류 삼키기로 통과시키지 않는다.
- 시험의 요청·대역 응답·기록 필드만으로 실제 장치 출력 종료나 무송신을 주장하지 않는다.
- 보존한 계약, 삭제·통합 이유, 실제 검사 범위와 남은 검증 경계를 처분 기록에 적는다.

### 2.10 완료 정의 (Definition of Done)

검사 통과는 완료가 아니다. 요청한 연결이 끝까지 동작했는지 판정하고 다음을 구분해 보고한다.

1. 소스·import·빌드 성공
2. 대역 통합
3. 실제 MATLAB 계산
4. 사용 가능한 실물 증거
5. 실물 준비 완료

최종 변경 뒤에는 다음 순서로 검토를 받는다. 모든 지적은 **"수정"** 또는 **"근거 있는 기각"**으로 처분해 기록한다.

1. **정적 분석(Iron Laws)**: 1회 실행해 지적을 의도된 계약·오탐(false positive)·실제 부채로 처분한다.
   바뀐 코드의 지적과 실제 결함으로 보이는 지적은 이번에 처리한다. 자동 등급만으로 수락하지 않고,
   지적을 억제하거나 기준을 낮춰 등급을 올리지 않는다.
   도구: [오철칙(Iron Laws)](https://github.com/JinHo-von-Choi/iron-laws) — `iron-laws check`/`audit`.
2. **독립 코드 리뷰**: 구현에 참여하지 않은 작업자(총괄이 있으면 총괄이 직접 배정한 독립 하위 에이전트)가
   현재 전체 구조를 읽기 전용으로 본다. 확인 대상은 실제 사용 경로, 입출력 계약, 실패 전파, 중복,
   시험 필요성, 이 문서의 기준이며, 표시되지 않은 코드도 포함한다.
3. **GPT Pro 코드 리뷰**: 기존 대화로 받는다.

### 2.11 인계 위생 (handoff hygiene)

- **문맥 압축·복구·세션 교대 뒤에는 편집이나 코드 검토를 재개하기 전에 이 정본을 반드시 다시 읽는다.**
  압축 요약이나 이전에 읽었다는 기록으로 정본 재독을 대신하지 않는다.
- 정본과 함께 현재 작업의 설계, 더한 것·뺀 것, 임시 코드와 제거 조건, 미처분 리뷰 지적을 확인한다.
  디스크에 이미 있거나 압축 요약에 기존 코드로 나왔다는 이유로 그 구조를 정당한 것으로 간주하지 않는다.
  이번에 덧댄 경로도 3절의 덧대기 기준으로 다시 판단한다.
- 안전 관련 코드·시험도 이 재판단에서 제외하지 않는다. 이전 담당의 "안전상 필요" 또는 "기존 구조"라는
  분류를 그대로 승계하지 않고 2.9의 실제 보호 계약과 검출 근거를 확인한다.
- 압축·교대용 인계에는 정본 경로와 위 재독 의무, 현재 추가·삭제·미처분 기록 위치를 남긴다. 재독은 기존
  검증을 무조건 다시 실행하라는 뜻이 아니며, 검증 재사용 여부는 변경 범위와 입력·계약의 동일성으로 판단한다.
- 보고·결과·인계 문서에 이번 변경에서 더한 것과 뺀 것을 함께 적는다. 다음 담당이 덧댄 코드를 원래 설계로
  오인하지 않게 하기 위해서다(Lava Flow 방지).
- 판·세션 이력("0.1.8에서 추가", "v0xx 호환")은 주석에 쓰지 않는다.
- 커밋은 한 논리 변경 단위의 원자적 커밋(atomic commit)으로 하고, 메시지에 이유와 지운 것을 적는다.

## 3. 덧대기 판정 — 이름을 바꿔도 같은 것

판정은 이름이 아니라 효과로 한다. 다음 중 하나라도 "예"이면 덧대기로 보고 원래 책임 자리에서 고친다.

1. 기존 책임 자리를 고치지 않고, 그 옆이나 위에 같은 일을 하는 길을 하나 더 만드는가?
2. 대체된 것이 지워지지 않고 남는가?
3. 다음 담당이 이것을 원래 설계로 오인할 수 있는가?

| 분류 | 이름만 다른 같은 형태 |
|---|---|
| 함수·모듈 | helper, utility·util·common·misc 모듈, 내부 함수 하나 더, 같은 계산의 복사·재구현, `_v2`·`_new`·`_old`·`_fixed`·`_safe`·`_strict` 사본 |
| 감싸기 | wrapper, adapter, facade, bridge, proxy, decorator, middleware, context manager, 호출 전후 전처리·후처리 단계 |
| 호환·우회 | shim, 호환층(compatibility layer), legacy 분기, 하위 클래스 재정의(override), mixin, monkey patch, hook·callback 주입 |
| 진입 경로 | 같은 일을 하는 새 entry point·runner·script·stage·CLI 옵션·모드 인자 |
| 분기·설정 | 기본값이 옛 동작을 유지하는 flag·option·매개변수, feature toggle, 환경 변수 스위치, 특정 입력만 위한 예외 분기(special-casing), 하드코딩한 예외·허용 목록 |
| 사후 보정 | 결과를 통과시키려는 clamp·재정규화·반올림, sleep·timeout 연장·retry로 타이밍 문제 가리기, 넓은 try/except, fallback 기본값 |
| 검사 | 기존 검사와 같은 일을 하는 guard·validator·재해시 층, 계층마다 같은 파일 재검증 |
| 시험 | 실제 경로를 우회하는 test double(mock·stub·fake·fixture), 시험 전용 hook, skip·xfail, 허용 오차·단정 완화, 제품 상수에서 가져온 기대값, 원인 없는 snapshot·golden 갱신 |
| 문서·기록 | 같은 규칙·설정 키의 중복, 아무도 읽지 않는 기록, 제거 조건 없는 "임시" 코드, 이력 주석 |

**정당한 경우**: 새 책임을 맡거나 실제 시스템 경계에 두는 adapter 같은 구조는 쓸 수 있다.
이때 다음 세 조건을 모두 지킨다.

- 대체된 경로를 지운다.
- 같은 일을 하는 길이 하나만 남는다.
- 보고에 그 이유를 적는다.

## 4. 보고 점검표 (작업자 보고·변경 기록에 붙인다)
